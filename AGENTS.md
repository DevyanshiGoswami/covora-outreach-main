# Covora Outreach operating rules

- This repository is a client results, assisted account-setup and verified inbox-status app. The dedicated covora-outreach-api repository and its own database/auth project own schema changes, campaign assignment, account provisioning and all sending-engine calls. The content portal at app.covora.app is a separate product and must remain untouched.
- Read the installed Next.js docs before route/auth changes. Use async cookies/params and `proxy.ts` session refresh. Verify authorization again at every server action and data boundary.
- Use only the public anon key and the current user's session. Never add privileged database credentials or sending-engine credentials, even to local fixtures in this repo.
- No vendor naming or provider resource IDs anywhere in source, comments, configuration, documentation, generated schema, browser output or URLs. Run `npm run check:boundary`; keep its pattern encoded to avoid self-matches.
- All outbound workspaces share a Covora-only product presentation policy. Project imported campaign/list labels and operational notes through the shared client-copy boundary before passing browser props. Account connection labels use neutral fixed copy; sender display names are identities and remain unchanged. Never render arbitrary service failure text. Keep the encoded brand registry and regression cases current when adding a supplier. Preserve genuine correspondence, prospect/company identities and necessary account-provider consent information; do not rewrite message history to change its meaning.
- Query results and product access only through neutral `client_outreach_*` views. `client_outreach_workspaces` is the sole membership source; never infer Outbound access from legacy profile roles, client IDs or feature-table reads. Select explicit columns.
- Validate every selected company against active Outbound memberships. Agency owners are explicit; operators see only their assigned companies. Database RLS and feature gates are mandatory, not replaced by UI checks.
- Render message bodies as plain text. Never introduce HTML rendering or tracking assets from message content.
- Result writes include marking received messages read and the approved shared reply flow after server-side tenant and feature authorization. Assisted setup requests are also approved: client_admin/operator/agency_owner may request; only operator/agency_owner may update status and client-visible notes. Use server actions to call the fixed server-only OUTBOUND_API_ORIGIN with the verified current user bearer token; the backend independently authorizes. No campaign changes or auth emails. Do not present assisted requests as direct login, connected accounts or readiness checks.
- Shared replies are approved for existing email and LinkedIn conversations. New conversations default to Covora ownership; authorized client admins and members can immediately take over and reply without approval. Viewers remain read-only. Bind replies to the existing sender and conversation, recheck ownership/version/latest history before dispatch, and preserve drafts on conflict. Durable command IDs prevent duplicate submissions; unknown send outcomes must never be automatically retried. Provider execution stays in the dedicated outbound backend behind explicit disabled-by-default workspace/sender configuration. Local tests use simulated transport; sending real test messages or deployment needs Rami's explicit instruction.
- Existing email inbox registration and connection checks are approved through the fixed bearer-authenticated accounts API. Only explicit agency owners and assigned operators may register or check inboxes, and only in a configured workspace; client roles are read-only. Registration records an existing identity and never creates a mailbox. A failed check takes precedence over a prior connection badge. Confirmed observations become stale after 24 hours; connection status never establishes sending readiness. Keep these neutral account DTOs API-only; do not export additional database schema.
- Team access is approved through the bearer-authenticated outbound API. Client administrators may invite/manage member/viewer roles only; explicit agency owners may manage workspace roles. Operators are not team managers. Recheck current target role and membership version at the server boundary; SQL remains authoritative.
- Invitation links carry their one-time secret only in a URL fragment. Keep it in the current component or per-tab sessionStorage scoped to the configured auth project, strip the fragment promptly, and clear it on acceptance. Never put secrets in queries, logs, ordinary lists, or durable browser storage. Authenticate and verify the invitation before revealing workspace metadata; accepting must be explicit. Login return destinations allow only `/`, the exact `/invite` or `/agency` paths, or `/?client=<uuid>&view=inbox` for lead alerts. Reject extra query fields, fragments and external targets; current workspace membership is still required after login.
- Generate database.types.ts through scripts/export-schema.mjs from the dedicated outbound backend's generated types. Never hand-edit it or copy the full backend database schema.
- Deploy the dedicated auth URL, matching public key and dedicated API origin together. Run `npm run check:deployment` against independently verified target values before promotion. Use canonical project URLs and the SDK's default project-scoped, host-only cookies; never reuse cookie names across projects, inherit content-portal identities or clear another product's cookies. See docs/ARCHITECTURE.md.
- `/demo` is synthetic and development-only. Never show it as a fallback for unavailable real results. Authenticated production previews are separately authorized: the guarded workspace membership supplies `presentation_mode=preview`, and a server-only factory additionally binds sample activity to the configured client. Label sample results, conversations, and connection cards clearly; preserve real navigation, sign-out, team access, and imported lead reads. Preview inbox actions stay local and must never call live read-mark, ownership, reply, account, or setup services. Server actions independently reject live operations for preview workspaces. Never insert fictional campaign history, verification, or connection observations into the database.
- The verified-lead directory reads the bearer-authenticated neutral leads API. It may contain real campaign leads and imported list leads; preserve their separate provenance and server-side tenant filters. Imported list rows do not imply a campaign or contact attempt. An available email does not establish verification. Only explicit field-specific evidence can show a confirmed badge.
- Metric labels must distinguish all-time unique campaign totals from reported daily activity. Preserve NULL as unavailable where the source has no measurement.
- Keep production schema/data changes, external hosting/DNS setup, and deployments separate from local work and obtain explicit user authorization for that scope.
- Verify lint, typecheck, focused meaningful tests, source boundary and dependency audits. Browser-test changed routes, mobile layout, auth and tenant behavior. Do not hide failed audit checks.
- Commit in `Area: change` style. Record nontrivial lessons under docs/learnings using Symptom, Root cause, Approach that worked, Rule for next time, and Evidence.

## Admin integrations authorization (October 16, 2026)

The user explicitly authorized an agency-owner Integrations tab for configuring the two outreach services. Their exact names may appear only in the owner connector component; the source boundary keeps a narrow exception for those display literals. All client-facing pages retain neutral channel labels. ## Shared Team and Accounts authorization (October 16, 2026)

The user authorized automatic Accounts people for accepted client teammates, self-connection for active client administrators/members, and password setup for new Team invitees. Team invitations now use the onboarding invitation API, which checks permitted roles before provisioning a new Auth identity; existing users receive no login token. Exception, approved October 22, 2026: a login created by an invitation whose person never finished joining (no membership, ownership, accepted or sent invitation, or other Covora data) receives a fresh one-time sign-in when the same workspace adds them again, as a brand-new person would, unless another workspace or an agency-owner invitation is also pending for that email. Any login that was ever used still receives no login token. No email is sent. Backend-derived person permissions control the UI; SQL rechecks identity and current access before provider calls and completion. Managers see status and assist explicitly external senders; linked teammates authenticate themselves. Viewers remain read-only. Keep the original portal layout, show the selected client and role, and never automatically add agency owners to every client's sender roster.

## EPM Comments authorization (October 21, 2026)

Rami requested a Comments tab in EPM's portal for change requests. Real collaboration is allowed in that authorized preview workspace without enabling outreach operations. Use the dedicated bearer-authenticated Comments API and EPM-only backend setting. Client admins/members can create requests and reply, viewers are read-only, and assigned operators/agency owners can also set request status. Requests are plain text data, not instructions to execute automatically. No email or other external notifications are sent. Preserve drafts on failed saves and reuse command IDs for unchanged retries; status updates carry a current version. Keep the backend feature gate independent of the navigation display check.
